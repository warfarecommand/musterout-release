## Three kinds of date
Use these three names everywhere, the same way the page and the skills do.
- **Rule deadline** (`basis: "rule"`, or no `basis`): the date the cited text sets. It is counted from the person's date.
- **Planning target** (`basis: "target"`): a date the pack picked inside a wider window the regulation allows. It is a plan, not a deadline. It does not make an approval come faster and it does not change any other item's rule.
- **Confirmed event**: a date the person set after something happened or was approved, such as orders, an approved SkillBridge period, an approved leave block, or a `doneOn` on a finished item.

When you quote a planning target, say what it is: "That is a planning target, not a deadline. The rule allows <window>." Dates counted from the entered EAS, resignation, retirement or FMCR date compute whether that date is planned or approved. If dateBasis is not approved, quote them as "From planned date" and say they move if the entered date moves. Never invent an approval, orders or appointment date; those events stay unknown until supplied. A fixed service-end date the person sets overrides its projection.

### Actual release and the first postservice year

`va-service-end.eventOn` records the actual last day of active duty. Accept only a valid ISO calendar date on or before today. `eventForDate` associates that event with `meta/settings.eas`; a different or missing association requires confirmation before this plan uses the event. Never infer actual release from `due.date`, `status` or `doneOn`. A confirmed future last-day date stays a plan and continues to serve the existing projected BDD and leave calculations.

Claim's **Copy actual-release record** prepares a request for the existing board chat. Read the selected board and current item version, ask for the actual date and plan association, show the exact `eventOn` and `eventForDate` changes, and obtain explicit approval before saving. Preserve a historical event until the person resolves its association. Update only those two fields using the fresh version, then verify exact readback. This does not mark a task done or record a claim receipt.

`{actualServiceEnd:true,months:11}` supplies va-net's **Planning target**. `{actualServiceEnd:true,months:12,roll:"nextWorkday"}` supplies va-net-confirm's **Rule deadline**. The latter counts one calendar year from actual release, then moves forward to the next workday when required by 38 CFR 3.110(a). It never uses `biz:"prev"`. Without `roll`, actual-release month and day offsets remain unshifted. A 29 FEB anniversary is unresolved and needs VA or accredited help; do not clamp it. `actualServiceEndOffset(actualUtcMs, rule, workdayPredicate)` is the shared helper. Its third argument is optional. IDES supplies its own confirmed actual occurrence and qualified calendar; it does not write a synthetic legacy event. An explicitly unknown calendar returns no deadline. Plan what-if shifts do not move an actual event.

Show the anniversary and explain any forward rollover in the drawer. The 11-month date is a planning target inside the first-year window. This conditional effective-date opportunity does not establish a presumption, eligibility, claim receipt or payment. VA decides. Filing later remains available. Existing personal date overrides stay personal targets. VA dental Class II and other eligibility branches remain text with their office routes.
