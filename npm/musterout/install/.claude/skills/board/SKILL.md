# /board

The URL is in `my/board.json`; that file holds the URL, pack, version, and created date, and no profile. Every personal fact comes from the live board. The board is the source of truth; read it before you answer.

## Read
- Overview: ArtifactData `get` on `meta/profile`, `meta/settings`, `meta/ledger`, `meta/seeded`, `meta/reset`, `meta/watch`, then `list` on `items` (limit 200, follow every page). If `meta/reset` exists, a reset stopped partway; say so and send the person to `/intake` before you change anything.
- Resolve dates the way the page does: `date` as given; `eas` plus N days; `serviceEnd` adds n days to the entered EAS/resignation day. On the retirement path, explicit `retirementKind: fmcr` uses the entered day and `retirementKind: retiredList` uses the preceding day. An existing retirement record without that choice keeps the page's enlisted month-end FMCR inference; choose the kind before saving a changed retirement date.  `byPath` selects the rule for the live path; `easMonths` by calendar month (clamped to the last day when the month is shorter); `sb` from `meta/settings.sbStart` or `sbEnd`, and when that value is null the item has no date and shows "Date pending SkillBridge approval" (never use the EAS in its place); Event item IDs: `ret-approval`, `sep-approval`, `sb-approval`, `ret-orders`, `sep-orders`, `eas-orders`; IDs ending in `-appt` are also event items. For a reference to an event item, use its `eventOn` only; without that date, the reference has no date. For other `item` references, use the referenced item's `doneOn` if set and its `kind` is not `milestone`; otherwise resolve its `due`. Add N days, or N calendar months when the rule has `months`, to that base in either case. Stop a repeated item reference or recursion beyond depth 128. Milestone references always use the scheduled due date. New-plan `va-exams` has no calculated due date or window. Follow actual VA appointment instructions. Preserve an existing legacy exam planning target and its actual `va-file.doneOn` anchor when recorded; label it as a planning target, not a VA deadline. Do not create a new 45-day agency deadline. A custom planning item can still reference a completed task or window. `biz: "prev"` uses the page's working-day calendar, including federal holidays. A rule that points at an item with no date resolves to nothing. Items with no date sort after dated items. For an event item itself, show `eventOn` when present; otherwise its saved due rule can still show a target. `min` selects the earliest resolved child, or no date if none resolve; `byPath` selects the live path. `unitDeparture` and `terminalStart` use the page's current leave/SkillBridge projections.
- Late means: a task or milestone whose resolved due is before today; a window whose `to` is before today. Markers are never late. Items with status done or na are never late. An item with no resolved date belongs in "Needs a date".
- There are three kinds of date. Name them the same way everywhere:
  - **Rule deadline**: `basis: "rule"` or no `basis`. The date the cited text sets. It is counted from the person's date.
  - **Planning target**: `basis: "target"`. A date the pack picked inside a wider window the regulation allows. When you quote one, say what it is: "That is a planning target, not a deadline. The rule allows <window>." A target does not make an approval come faster and does not change any other item's rule.
  - **Confirmed event**: a date the person set after something happened or was approved. Record it with a `date` rule from orders or approval, or with `doneOn`.
- Deadlines counted from the entered date compute before approval. When profile.dateBasis is not approved, quote them as "From planned date" and say they move if the entered date moves. Actual approvals, orders and appointments stay undated until supplied. A fixed va-service-end date overrides its projection.
- Next: open items due in the next 14 days, critical first, then open windows that are open today, then critical items with no date.
- Read `blocks` for leave. Read `conditions` and `claim` for the claim. Contacts and sources use `contacts`, `links` and `inbox`.

## Seed records the page keeps
You read these; you never write them during a seed. The page writes them.
- `meta/seeding`, the claim while a seed runs. The page takes it, renews `claimedAt` every 30 seconds, and treats it as expired after two minutes.
```json
{"claimedAt": "2026-10-09T15:05:00Z", "by": "a8K3pq", "profileKey": "resign|o14|true|false|2027-09-01|null|null"}
```
- `meta/seeded`, the marker after a seed. `count` is the number of seeded items; `pack` is the pack version.
```json
{"at": "2026-10-09T15:06:10Z", "count": 74, "profileKey": "resign|o14|true|false|2027-09-01|null|null", "pack": "usmc-2026.10"}
```
- The page seeds only under the runtime's `acquire` lease on `meta/seeding`. A browser without it shows a lock message and does not seed; tell the person to open the board in a current browser or the Claude app. Never write the seed by hand.
- The profile key is `path|grade|reserve|sb|eas|sbStart|sbEnd` from `meta/profile` and `meta/settings`, joined with `|`, booleans as `true` or `false`, nulls as the string `null`.
- Mismatch rule: when `meta/seeded.profileKey` differs from the live key, the page does not reseed. It shows "Your path or dates changed since the plan was seeded. Run /intake reset to rebuild the plan, or Edit profile to keep this one." It still recomputes dates from the live settings. To keep the plan, pin the update of `meta/seeded.profileKey` to the live key. To rebuild it, `/intake` reset.
- A seed writes only ids that are absent. It never overwrites an item, line of effort, contact, or claim document that exists.

## Write
The person's own records can stay as they are in their private Project, including files with identifiers. Never repeat SSNs, DoD IDs, VA claim numbers, account numbers or similar identifiers in replies, or store or write them to their board or your notes. Strip them and other people's personal details from drafts for others, including call briefs, spouse briefs and advisor notes. Never ask for an SSN, password or CAC PIN.

Every write to an existing document carries `if_version` from the read. Prefer one `batch` over many calls.
- Status: update `items/<id>` with `status` and, for done, `doneOn` in YYYY-MM-DD. Ask when it happened when another item's date depends on it; use today only if they say today. Statuses: open, doing, waiting, done, na.
- Notes: update `notes` on the item. Keep the person's words.
- Items may carry optional seed-owned `after: [IDs]` for informational Needs and Unlocks links; it never changes dates or blocks action, and Today Ready means all linked steps are explicitly done or not applicable.
- New item: set `items/<id>` with every field: id, loe, order, kind, title, why, how, owner, due, window, basis, critical, presence, cite, verify, status, doneOn, notes and user. Use a kebab id with prefix `u-`. Kind is task, marker, window or milestone. Use lists for how and cite; each citation has ref, para, quote and url. Due is a rule; window is null or from and to rules. Basis defaults to `"rule"`; use `"target"` for a planning target. Start with status open, doneOn null, notes "" and user true. Cite the pack or set `verify`. A date the person sets from orders or an approval is a confirmed event: write it as a `date` rule and say so in `notes`.
- Change a date rule: set the whole item, or update with the old rule key as `{"__delete__": true}` in the same write. Update alone deep merges and leaves the old key, and the old key wins.
- Change the EAS: first list what stays put: items with a `date` rule and references anchored to a non-event, non-milestone item's `doneOn`. Milestone references follow the milestone's scheduled due rule even after confirmation is checked off. A fixed milestone date stays fixed; an EAS-based milestone moves with EAS; a SkillBridge milestone follows `sbStart` or `sbEnd`. Recorded event dates stay fixed. Actual filing completion can anchor a preserved legacy exam planning target; new exam items use actual VA instructions without a calculated agency deadline. Show the fixed dates and ask which should change too. Then update `meta/settings` `eas` with `if_version` from the read. Update `sbStart` and `sbEnd` if the SkillBridge period changes with it. In the same batch, update `meta/seeded.profileKey` to the new live key, because the person chose to keep this plan. The page recomputes every date counted from the EAS. If the date is now approved, update `meta/profile.dateBasis` to `"approved"`.
- Leave block: set `blocks/<id>` with id, start, end, status (approved, requested, known, planned, cancel), away (true if out of the area), kind (leave, liberty, ptad), note and updated.
- Condition: set `conditions/<id>` with `{id, name, status, code, side, limb, words, rule, todo, evidence, exam, note, record, src, updated}`. `status` is one of needs visit, in records, seen, in claim or rated. `limb` is null or one of LUE, RUE, LLE, RLE (the page's bilateral math reads it). `todo` and `evidence` are lists of strings; `record` is a list of `{date, entry, src}`; `src` is a list of `{label, url}` with https URLs only. Never write `est` or `scen`; criteria choices and combined estimates stay in page memory. The VA module is free. Support self-help: the Marine prepares, edits, signs and files their own claim. Show official rating criteria, let the person choose a tier, then use the existing combined-rating math and current official pay table. Label the result "Estimate. VA decides." Never choose a tier for them, invent findings, represent or file for anyone, give a claim-ready or evidence-sufficiency verdict, or coach exaggerated or scripted symptoms.
- Claim documents, each with exactly these keys: `claim/where` `{rows: [{appt, where, home, base, how}], note}`; `claim/vso` `{rows: [{rank, name, why, phone, email}], script, note, updated}`; `claim/exposure` `{rows: [{location, hazards, presumptive, action}], notes: [string]}`; `claim/benefits` `{title, label, rows: [{what, detail}], note}`.
- Contact: update `contacts/<id>` name, phone, email, note.
- Profile: update `meta/profile`; changing path, grade, Reserve, or SkillBridge after seeding does not add or remove items, and it changes the profile key. Offer two choices: keep this plan (add or retire the affected items by hand, citing the pack, then update `meta/seeded.profileKey` to the live key) or `/intake` reset to rebuild it.

### IDES event record

For profile.path=ides, read meta/ides (schemaVersion 1) separately from meta/settings. It holds administrative event occurrences, explicit requirement/clock selections, branch confirmations, authority calendars and separate projections. An initialized IDES path may seed without an EAS. Confirm the matching seed key/count and event readbacks before reporting ready.

Use the page's Confirm event controls. If helping with an expressly requested native write, show the factual administrative change for review. Take a fresh version. Preserve every occurrence and unknown field with changed-field update. Events and selections use occurrence-keyed objects; branch and calendar confirmations keep occurrence histories. Renew the same-holder lease immediately before writing. Read back your change and all records from the fresh read; on any conflict, keep the draft visible. Never set the whole meta/ides document or delete a superseded entry. No receipt may come from due.date, doneOn, notes, an estimate, a scheduled date passing or a rating. Actual dates cannot be future. Corrections supersede previous occurrences and invalidate affected selections. Keep counsel, care, Wounded Warrior and VA help available while facts or calendars remain unresolved. Never store IDES events inside meta/settings or fabricate a legacy eventOn field from them.
